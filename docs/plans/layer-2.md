## 4. Screens

**Resident PWA (`apps/web-resident`, every screen axe-clean on desktop and phone, keyboard-only path tested, 200 % zoom, 320 px reflow)**

1. Welcome: county name, language picker in each language's own script, 911 line, "about 5 minutes, no account", witness and helper entry points (mockup `Main`).
2. Safety first: "Is anyone in danger right now?" → yes shows the locally approved emergency instructions and records the flag; the report continues afterwards (mockup `Safety`; INT-07, CON-10, ACC-48).
3. Who is reporting: own home / helping someone / saw damage / several properties (WIT-01, HLP-01, ORG-01).
4. One question at a time from the graph with "About N questions left" in words, "I don't know" and "Skip", one example and one reason per question, picture choices for damage type, hazard branches (mockups `Question`, `HomeType`, `Insurance`).
5. "Or tell us in your own words": typed or dictated (browser speech API where available); extracted candidates shown as "You said … is that right?" with one-tap confirm or edit; "A computer helped fill in these answers" notice with an off switch (INT-12–14, AIG-10).
6. Photos: guided shot list by hazard with examples and the safety line; camera or gallery; client-side compression and EXIF read for a suggested date and place, then stripped; blur and darkness check with one retake suggestion; skip always allowed (mockup `Photo`; PHO-01–06).
7. Needs and consent: "Do you need help with any of these?" multi-select with icons; consent per organization type in plain words, default no (NED-01–03).
8. Review: grouped "Your home / What happened / What you need", each editable, extracted answers marked (mockup `Review`; INT-21).
9. Send: outbox with "Not sent yet / Sending / Received" states, retry with backoff, one report per execution id (ACC-39, AC-11B).
10. Confirmation: reference code in text and QR, "text this number to me", what happens next without promising aid, shared-device clearing (mockup `Confirm`; INT-22, FL-01, ACC-30/41/50).
11. After saving: optional questions (household, access needs, hurt or missing, lost work, demographics, accommodation request), each with its purpose (INT-19, EQ-13, DCL:DEC-01, ACM-01).
12. My report: reference code + one-time code → status, consent changes, corrections, withdrawal (RES-01/02).
13. Pause and resume with a code (INT-20).
14. Assisted / kiosk mode (`/assist`, staff sign-in): records helper, affected person and consent; offline outbox in encrypted local storage; session cleared on completion (CHN-06/07).

**Console (`apps/web-console`)**

1. Review queue: need signals first, then severity (none in layer 2), then age; filters by event, state, verification, channel, duplicates (CON-05, PHO-14).
2. ## 5. Channels

- **SMS (CHN-03/04, `docs/06`):** keywords DAMAGE / DAÑOS / DANOS start the flow in that language; SHELTER / REFUGIO answer with the county help line and "find help" link until layer 3 publishes resources; numbered answers; BACK, SKIP, HELP/AYUDA, STOP/ALTO and the carrier opt-out words always work; MMS photos attach to the current question; opt-in confirmation, HELP and STOP replies use the `docs/06` templates with the county's name, never the product name; the first reply carries the reference code and "In danger now? Call 911".
- **Voice (CHN-05):** TwiML with `<Gather>` speech and keypad in English and Spanish, same graph, "press 0 or say agent" transfers to the tenant's help line; the recorded greeting from `docs/06`.
- **Assisted and kiosk (CHN-06/07):** the shared renderer inside the console and the PWA's `/assist` mode; helper, affected person and consent recorded; offline capture with an encrypted outbox; "Not sent yet" until the server confirms.
- **Comms adapter:** `sendSms`, `sendMms`, `startCall/TwiML`, `parseInbound`, `verifySignature`, `statusCallback`. Simulator for development and tests (an HTTP endpoint and a console page listing sent messages, like Mailpit for email); Twilio client for real numbers. Webhooks reach a laptop only through the secured tunnel (CLAUDE.md rule 3).

## 6. AI in this layer (interfaces, not providers)

`packages/ai`: one interface each for language model, speech-to-text, translation and image analysis (AIG-12); a deterministic fake provider for all four; provider selection per tenant from configuration with the AIG-06 attributes recorded in the register; every output records provider and model. The extraction prompt treats resident text as data in a delimited field (AIG-02), returns a fixed JSON schema validated server-side (AIG-03), redacts names, phone numbers and exact addresses before any external call (AIG-05), and passes an output filter that drops eligibility statements, promises, medical or legal advice (AIG-07). An evaluation harness with a labelled multilingual set (English, Spanish, code-switching, low-literacy phrasing) and prompt-injection cases runs in CI against the fake and blocks a provider that regresses (AIG-08). Residents are told and can turn it off (AIG-10). Real providers are a layer-7 decision with Adam (paid services).

## 7. Photos

Direct resumable upload to object storage (SCL-04). The worker strips EXIF and makes derivatives (PHO-06) with `sharp`; originals stay under a restricted prefix readable only by reviewer roles (PHO-07, AC-10C); blurring of faces, plates and documents runs through the image-analysis interface, whose fake provider reports "no detector", so derivatives stay restricted until a real detector exists (layer 7) and the status says so plainly; nothing public ever shows a resident photo (PHO-08). Exact duplicates by hash and address duplicates are flagged for a person (PHO-15, part).

## 8. Abuse protection (SEC-17, BRD:FR-11.05)

No CAPTCHA. Per-IP and per-phone token buckets in the API, a risk score from velocity, repeated content hashes and malformed payloads, and a one-time SMS or email verification only when the score is high. Assistive-technology users are never challenged by the score alone; the verification step is itself accessible (ACC-43/44). Decisions are recorded in `abuse_signal` and audited.

## 12. Ambiguities resolved in the resident-protective direction (flagged for Adam)

1. **Reference code lookup contact (SEC-09):** the one-time code goes only to a contact the resident gave at submission; a report without contact details can be viewed only in person with a helper (assisted mode) and never by code alone.
2. **Danger flag (CON-10):** the resident is told to call 911 on every channel; the flag records the time; no staff notification is treated as a dispatch, and the queue shows the flag as awareness only.
3. **Witness reports (WIT-01):** stored as a separate relationship, never merged into an owner's record automatically; a reviewer may link them as evidence.
4. **Organization reports (ORG-01):** each property is its own report with its own reference code; the organization is the reporter party, contact details are shared across them, and consent is per property.
5. **Pause codes (INT-20):** six characters, hashed at rest, seven-day expiry, no personal data in the code; resuming shows nothing until the code matches.
6. **Risk-based verification (SEC-17):** a high score never blocks a submission (rule 8). The report is accepted, carries a "contact not verified" signal for reviewers with the reasons, and the resident can verify through the reference-code lookup (one-time code to the contact given, never a puzzle). Only a flood from one network address is refused, with a retryable 429 and the county help line.
7. **Photos before blurring (PHO-07):** restricted to reviewer roles; the queue shows a placeholder and the reason; nothing is lost.
8. **SMS keywords (CHN-03):** DANOS without the tilde is accepted as Spanish because many phones drop it; AYUDA stays the help keyword; SHELTER and REFUGIO reply with the help line until layer 3.
