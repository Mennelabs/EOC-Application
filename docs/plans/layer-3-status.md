# Layer 3 status

The coordination record for layer 3 (needs board, partner sharing with consent, public "Find help"). Any session resumes from this file, not from chat. Update it in every commit that changes a task's state. Plan: [`layer-3.md`](layer-3.md). Decisions: [`../decisions.md`](../decisions.md). Layer 2 record: [`layer-2-status.md`](layer-2-status.md).

## Resume checklist

1. `pnpm install && pnpm typecheck && pnpm test && pnpm lint && pnpm check:product-name` green before new work.
2. Stack for integration work: `scripts/init-env.sh` (or `scripts\init-env.ps1`) then `docker compose up -d --wait`; `COMPOSE_PROFILES=maps` for the tiles and geocoder.
3. Pick the first task below that is not `done`, finish it to green, commit citing requirement IDs, update this file, push.

## Known issues and deferred items

- See `layer-3.md` §11 for deferred IDs and §12 for the readings taken in the residents' favour.
- Two text keywords are new (`NOSHARE`, and `SHELTER`/`REFUGIO` now answer with sites): `docs/06` carries the NOSHARE row since task B (flagged for Adam before the carrier submission); the SHELTER/REFUGIO change lands in task E.
- Partner reads are audited in the partner's tenant; the county's audit log shows grants, updates and revocations but not each partner read. A county-side read ledger (one row per partner read on the grant) is planned for task H.
- Email replies to staff updates are not captured by the system (task E): the email asks the resident to reply, and the reply lands in the county's own mailbox. Capturing inbound mail needs an inbound mail route (a paid service decision for Adam).
- Partner actions on the board (claim, release, done) run inside the county's RLS context through `request.txAs`, after the grant is verified in the partner's own context and only for that one need; they are audited in the county's log with the partner account as actor. Keep `txAs` to grant-covered records (documented on the decorator).
